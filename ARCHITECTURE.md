# Architecture

rem has two Gradle modules. `:core` is plain Kotlin with `java.time` and no Android imports. `:app` is the Android application.

## :core (`dev.balaji.rem.core`)

All the rules live here, as pure functions and small value types, with unit tests.

- `Alarm` and `Alarm.nextDeadline(after, zone)`. An alarm carries its own tone, vibration, volume floor, volume ramp, snooze length (1 to 30 minutes) and snooze limit (0 to 10, where 0 turns snooze off), with ranges and `coerced()` on its companion. The alarm time is the local "must wake by" deadline. Next occurrences are computed per calendar date in the zone, so daylight saving shifts keep the wall clock time. A time in a spring-forward gap resolves to the start of the gap. A time in a fall-back overlap rings once, at its first occurrence.
- `SleepSession` with `covers(deadline)` (after the start, up to 16 hours later) and `isActive(now)`. `acceptedLate` maps each alarm whose late option the user accepted in this session to the deadline it was accepted for, and `acceptsLate(alarmId, deadline)` holds only for that pair, so the consent does not follow an alarm edited to another time. With any accepted, the session stays active `LATE_WINDOW` past its 16 hours, so a late ring at the very end still belongs to it.
- `RemSettings` with defaults, ranges and `coerced()`. It holds what applies to every alarm: the cycle settings, headphones only and the speaker fallback time. It is not called `Settings` so it does not clash with `android.provider.Settings`.
- `computeWakeTime(deadline, session, settings, now, acceptLate)` returns the ring instant, a `WakeExplanation` (`Cycles(cycles, minutesBeforeDeadline)`, `LateCycles(cycles, minutesAfterDeadline)` or `AtDeadline(reason)`) and the late option. When no cycle ends before the deadline inside the early window (`NO_CYCLE_IN_WINDOW`, `BEFORE_FIRST_CYCLE`), the first cycle boundary after the deadline is the `LateOption` if it is at most `LATE_WINDOW` (30 minutes) after it. Only `acceptLate` moves the ring there. Nothing ever rings later than the deadline plus `LATE_WINDOW`.
- `planSchedule(alarms, session, settings, clock, lastFired, previous)` returns a `SchedulePlan`: one `PlannedRing` per enabled alarm, each with its late option. `planRing` plans one alarm. `SchedulePlan.lateOffers(session, settings)` lists the late options a new session would offer, for the prompt on "going to sleep". `checkMissed(previous, lastFired, now)` finds rings that should have fired. A ring is due at its deadline, or at its ring time when that is later.
- `ScannedCode`, `BarcodeKey`, `Barcode` (no owner field, storage says which alarm a barcode belongs to), `normaliseBarcode`, `Collection<Barcode>.findMatch`, and `StableScanFilter` (same code in 2 consecutive frames).
- `FallbackCode.generate` and `FallbackCode.matches` for the 40 character typed escape hatch.
- `RingLimits.MAX_RING` is the 30 minute limit on one ringing stretch. The first ring and each ring after a snooze are separate stretches. `RingLimits.QUIET_PERIOD` is how long a ring stays quiet while the user scans or types the code (60 seconds).

## :app packages

| Package | Holds |
|---|---|
| `data` | Repository interfaces, `RingStateStore`, `DataModule`. `data.db` is Room (`RemDatabase`, alarms and barcodes, `Migrations.kt`). The migration to version 2 gives every alarm the old default volume floor and ramp and turns headphones only off, because it cannot read the version 1 values from DataStore. The migration to version 3 adds the snooze length and limit at their defaults. Each barcode row belongs to one alarm through a foreign key that deletes it with the alarm, and is unique per alarm and key. `data.store` is Preferences DataStore (settings, sleep session, ring state). |
| `schedule` | `AlarmScheduler` and its implementation `AlarmManagerScheduler`, `AlarmClocks` (the `setAlarmClock` calls), `AlarmReceiver`, `RescheduleReceiver`, `AlarmBroadcast`, `ScheduleModule.kt` |
| `ring` | `RingController` and `DefaultRingController`, `RingingService`, `RingNotifications`, `RingActionReceiver` (the Snooze and Dismiss notification actions), `RingingActivity`, `RingModule.kt`. `ring.audio` is the player, headphone routing, volume floor and vibration, and `AlarmTonePreviewPlayback`, which the editor's play button uses. `ring.ui` is the ringing, scanner and typed fallback screens. |
| `scan` | `BarcodeScanner` composable and `ScannerCamera` (CameraX with the bundled ML Kit model) |
| `ui` | Every non-ringing screen with its view model, navigation, theme, `AppLinks`, `ui.system` (system checks and settings openers) |
| `di` | `AppContainer`, `DefaultAppContainer`, `SystemZoneClock`, access helpers |

`MainActivity` and `RemApplication` sit in the root package. Strings are in `strings_ring.xml` (`ring_` prefix) and `strings_ui.xml` (`ui_` prefix), with `strings.xml` for the app name and screen titles.

## Wiring

There is no DI framework. `RemApplication` holds one `DefaultAppContainer`. Get it with `context.appContainer`, or `LocalAppContainer.current` in Compose. Build view models with `containerViewModel { MyViewModel(it.alarmRepository) }`. `containerViewModel(owner) { ... }` scopes one to another back stack entry, which is how the scan screen reaches the editor below it.

`DefaultAppContainer` never names a concrete class. It calls one module file per package:

- `DataModule(context)` opens Room and three DataStore files on `context.createDeviceProtectedStorageContext()`. One instance per process, because DataStore rejects a second instance on the same file.
- `createAlarmScheduler` builds `AlarmManagerScheduler`.
- `createRingController` builds `DefaultRingController`. It reaches the scheduler through a lambda, so neither is created inside the other's constructor.
- `createAlarmNotifier` builds `RingNotifications`.

Everything in the container is lazy. `applicationScope` has a `SupervisorJob` and an exception handler that logs, so failed background work does not kill a process that may be ringing.

The in-memory repositories (`data.fake`) and the stand-in controllers and schedulers are in the test source set only.

## Who writes what

- The UI writes alarms, barcodes, settings and the sleep session through the repositories, including `acceptLate(alarmId, deadline)` and `revokeLate` for an alarm's late option in the active session. Starting or ending a session forgets them. It does not call `rescheduleAll`. The scheduler collects the alarm, session, settings and ringing-record flows and reschedules itself.
- The UI reads ring times and explanations from `AlarmScheduler.plan`. For previews it calls core directly: `planRing` for the alarm in the editor, `computeWakeTime` for "if I sleep now" on home, which also names the late option that ring would have.
- Late options reach the user in two places. "Going to sleep" starts the session at once, then `HomeViewModel` calls `lateOffers` on the plan from before the session and, if there are any, shows `LatePromptDialog` with one switch per alarm, all off. Only "Done" writes `acceptLate`, with each offer's deadline, and only into the session the prompt was made for. While a session runs and the ring's deadline is ahead, an alarm card whose planned ring has a late option offers "Ring at 06:15 instead" (`acceptLate`), or "Back to 06:00" (`revokeLate`) once the ring's explanation is `LateCycles`. Once the deadline has passed the card offers neither, and the view model ignores a tap sent by a card that had not caught up: going back to a passed alarm time would ring at once.
- `schedule` writes `RingStateStore.markFired`, `retainFired` and `setScheduled`. It disables a one-shot alarm whose only occurrence was missed. It revokes the late consent of an alarm that is switched off or deleted.
- Barcodes are edited only in the alarm editor. `AlarmEditorViewModel` is the `BarcodeTarget` of the scan screen (`BarcodeScanRoute`, opened from the editor), which checks a scan against the alarm's barcodes and hands a new one back. For a stored alarm the editor writes added, renamed and deleted barcodes at once. A new alarm holds them in the view model until save.
- A duplicate is a new alarm. "Duplicate" opens `AlarmEditorRoute(copyFromId = id)`, and the view model copies the stored source alarm into its draft and the source's barcodes into its unsaved list. From an existing alarm's editor the copy opens on top, so that editor's unsaved changes are still there when the copy closes, but they are not copied.
- `AlarmRepository.upsertWithBarcodes` saves an alarm and barcodes for it in one transaction, so a new alarm and its first barcodes are stored together. `upsert` updates a row in place and never replaces it, because a replace would delete the alarm's barcodes through the foreign key.
- The editor's play button (`RingtoneRow`) plays the alarm's tone through `TonePreview`, which holds no Android code, and `AlarmTonePreviewPlayback`, which reuses `AlarmAudioPlayer` and `AlarmVolumeFloor`: the alarm stream, the bundled tone when none is picked, the alarm's volume floor and no ramp. It stops on a second tap, on another tone, when the editor stops or leaves composition, and when an alarm starts ringing, and the button is off while one rings. A ring shown as a heads-up leaves the editor on screen, so `RingPlayback.start` also calls `AlarmTonePreviewPlayback.stopActive()` before it touches the volume. Otherwise the ring's volume floor would save the level the preview raised and put that back when the ring ends. The system ringtone picker cannot play the bundled tone and plays its own previews at the current alarm volume, which is why the editor has its own button.
- `ring` writes `RingStateStore.setRinging`, `clearRinging`, `snooze` and `clearSnoozed`, disables one-shot alarms when their ring ends, and ends the sleep session when a ring it covers is dismissed. A snooze does neither. It calls `removeFired` when a ring ends undismissed with its deadline still ahead.

## From "alarm saved" to "barcode scanned"

1. Something changes: an alarm is saved or toggled, "going to sleep" or "I'm up" is pressed, a setting changes, the process starts, the device boots, the clock or zone changes. Each of these ends in `AlarmScheduler.rescheduleAll()`.
2. `rescheduleAll` runs under a mutex. It ends a session older than 16 hours, runs `checkMissed` on the rings it persisted last time and reports misses through `AlarmNotifier.notifyMissed`, runs `planSchedule`, sets one `setAlarmClock` alarm per planned ring with `AlarmBroadcast.fireIntent`, cancels the rest, persists the rings with `setScheduled` and publishes `plan`. Setting the alarms is the part that must happen. Every read and write around it is caught and logged, so a failing write cannot stop the alarms from being set. More details:
   - If a ring became due under 2 seconds ago and has no fired record yet, the run first waits out those 2 seconds. Setting an entry again would cancel a broadcast that is still on its way.
   - A ring that looks missed is not reported by the run that first sees it. That run starts another one 5 seconds later, which reports the ring if it still has no fired record. Right after a process start or a clock jump the alarm broadcast can be queued behind the reschedule. The alarm that is ringing or snoozed is never reported.
   - A one-shot alarm that is ringing or snoozed is left out of the plan. The ring disables it when it is dismissed. Once it has been edited to another time it is planned again.
   - A late ring comes after its deadline, so between the two the alarm's next deadline is already the following one. `planRing` keeps the occurrence planned instead: the occurrence whose late option the session accepted, at the deadline it was accepted for, stays planned while it has not fired and its late ring is still ahead. This needs only the session, so it survives a process death or a reboot. Switching the alarm off revokes the consent, so switching it back on before the late ring plans its next real occurrence. A late ring among the persisted rings whose time is still ahead is owed too. If it is no longer late (the option was revoked, the session ended or was replaced, a setting removed the boundary) it rings at once, because its deadline has passed. A late ring whose time passed without a fire is reported as missed. An alarm edited to another time drops the occurrence.
   - A fired record is ignored when the alarm no longer has an occurrence at that instant, so editing an alarm after it rang early does not skip a day. A fired record more than 90 minutes ahead of the clock (the largest early window) was written under a clock that has moved back since, and is deleted. Fired records of switched-off alarms are deleted too.
3. At the ring time AlarmManager sends the broadcast to `AlarmReceiver`. It reads the `ScheduledRing` from the intent and calls `RingController.startRinging(ring)` at once. Then, under `goAsync()`, it calls `RingStateStore.markFired(alarmId, deadline)` and `rescheduleAll()`. The fired record is what stops an alarm that rang at 06:45 for a 07:00 deadline from being planned again for 07:00. When `startRinging` returns false (another alarm is ringing, or the service could not start) the record is written only if the deadline has passed, so a lost early ring is planned again at its deadline. A late ring is always past its deadline, so a lost one is recorded and reported as missed.
4. `startRinging` claims the ring, so `RingController.state` is `Ringing` before it returns, and starts `RingingService` with `RingContract.serviceIntent`. The service calls `startForeground` (type systemExempted) with a notification whose full-screen intent and tap open `RingingActivity`. The controller then loads the alarm, that alarm's barcodes and the settings, persists a `RingingRecord` and tells the service to play. The tone, vibration, volume and snooze come from the alarm, headphones only and the speaker fallback from the settings. Barcodes that cannot be read, also at the second try, leave no plain stop button, only the typed code.
   - Until the alarm is loaded the ring counts as needing a barcode, and the notification's only action is "Scan to dismiss", which opens `RingingActivity`. Once `RingSpec` arrives the service rebuilds the notification: Snooze while snoozes are left, then "Scan to dismiss" for an alarm with barcodes or Dismiss for one without. Snooze and Dismiss are broadcasts to `RingActionReceiver`, which calls `snooze()` or `dismissWithoutBarcode()` on the controller without opening anything. It acts only when the ringing alarm is the one the action was shown for.
5. The service follows the controller's `command` flow (`Wait`, `Play`, `Stop`) and decides nothing itself. `Play` carries a `quiet` flag, and a change of that flag alone pauses or resumes the same playback instead of starting it again. `RingPlayback` plays the tone on the alarm stream with a volume ramp, vibrates, keeps the alarm volume at the alarm's floor and, with the headphones-only setting on, pins the output to a connected headphone until it disconnects, the route turns out wrong or `speakerFallbackSeconds` pass. The vibration is one request per 2.25 second cycle, because the system cancels a vibration when the screen turns off. If Do Not Disturb mutes alarms it asks for vibration even when the alarm has vibration off, but the system may block an alarm vibration together with the tone. The reliability check for Do Not Disturb is what the user has to rely on there.
6. `RingingActivity` shows the ringing screen over the lock screen. "scan to dismiss" opens the scanner screen, which hosts `BarcodeScanner`. "can't scan?" opens the typed fallback, which asks `newFallbackCode()` for a fresh code. An alarm without barcodes has a plain Dismiss button instead. While the ring has snoozes left a button above them says "snooze 5 min (2 left)".
   - The taps that open the scanner or the typed fallback call `startQuietPeriod()` (`RingNavHost`), so once per visit. The screens do not, so a rotation does not extend the quiet time and a scanner restored from saved state after a process death leaves the resumed ring loud. The controller then publishes `quietUntil` in `state` and `Play(quiet = true)`, and `RingPlayback` pauses the tone and the vibration. The volume floor, routing and audio focus stay, and the activity still swallows the volume keys. Both screens show the time left.
   - The ring is loud again when the period runs out without a dismissal, or at once when the ringing screen is resumed again (`endQuietPeriod()` from a `LifecycleResumeEffect`), which is what going back does. A predictive back gesture only brings the ringing entry to STARTED while it previews it, so a cancelled gesture keeps the quiet. Opening the scanner or the typed code again starts a fresh period. The quiet time counts toward the 30 minute limit, and the watchdog keeps running. Quiet state is only in memory, so a ring picked up after a process death starts loud.
7. `BarcodeScanner` reports a barcode once it was seen in 2 consecutive frames. The screen passes it to `RingController.dismissWithBarcode`. The controller compares it with the ringing alarm's barcodes as they were when the ring started, using `findMatch`. Barcodes of other alarms do not count. With none on the alarm `state.requiresBarcode` is false and `dismissWithoutBarcode()` works instead.
8. On dismissal the controller tells the service to stop, which restores the volume. It clears the `RingingRecord`, disables the alarm if it is one-shot and still set for the time that rang, ends the sleep session if it covers the ring's deadline (a late ring's session still does) and calls `rescheduleAll`. `state` becomes `Idle` and the activity finishes.
9. A snooze (`snooze()`) needs no barcode. The controller first sets an alarm clock entry for now plus the alarm's snooze length (`SnoozeAlarms`, implemented by `AlarmClocks`, intent from `AlarmBroadcast.snoozeIntent`). Each alarm's entry has its own PendingIntent identity, so `rescheduleAll` never touches it. If the entry cannot be set the snooze is rejected and the ring goes on. Then the service stops, the quiet period and the watchdog end, the record moves to the snoozed rings in `RingStateStore` (`snooze`) with one more snooze counted and the time it rings again, and an ongoing "snoozed until" notification is posted. `state` becomes `Snoozed` and the activity finishes. The session and a one-shot alarm stay as they are, and so does the fired record.
   - When the entry fires, `AlarmReceiver` calls `endSnooze`. It claims and starts the ring like `startRinging` does, but continues the snoozed record: the barcode rule, the barcodes and the snooze count carry over, and the stretch starts now with a fresh 30 minutes. A resumed ring and a ring after a snooze do not ask whether the alarm is still enabled. A snoozed record that is gone means the snooze was dismissed, and nothing rings.
   - Once the alarm's limit is used up `snoozesLeft` is 0, the screen and the notification offer only the dismissal and `snooze()` is rejected.
   - Tapping the snoozed notification opens `RingingActivity`. With nothing ringing it shows the snoozed ring that comes due first, until when, and "dismiss now": the scanner and typed code for an alarm with barcodes, a plain button for one without. The same dismissal calls act on it. Dismissing it cancels its entry and notification, clears its record and does what a dismissal of a ring does.
   - Home shows "Snoozed until 06:25" on the alarm's card and a banner that opens the snoozed view.
10. If nobody dismisses or snoozes within 30 minutes of the start of a stretch the controller ends the ring, the session stays and a missed-alarm notification is posted. If the deadline is still ahead (possible with an early window above 30 minutes) the fired record is removed and a one-shot alarm stays on, so the alarm rings again at the deadline. Otherwise, which includes every late ring, a one-shot alarm is disabled.
11. A second alarm that comes due during a ring does not interrupt it. If its deadline is still ahead it is planned again for the deadline. If its deadline has passed, as it always has for a late ring, it gets a missed-alarm notification and is disabled if it is one-shot. A snoozed alarm is not ringing, so other alarms ring as usual while it waits. A snooze that comes due during another ring is not missed: `endSnooze` leaves it alone, and when that ring ends, by any route, the controller sets the snoozed ring's entry to fire at once, so it rings next with the alarm clock allowance. With several snoozes due the earliest goes first.

## Reboot and process death

`RemApplication.onCreate` runs on every process start, including before the first unlock. It calls `ensureChannels()`, then `RingController.recoverInterruptedRing()`, then `rescheduleAll()`.

A ring that was cut off comes back, for as long as its 30 minutes have not run out. Three paths lead there, and all of them keep the start time of the persisted `RingingRecord`, so the limit counts from the start of the stretch.

- The watchdog. While a ring is live the controller keeps one more `setAlarmClock` entry 60 seconds ahead and pushes it forward every 20 seconds (`RingWatchdog`, implemented by `AlarmClocks`, intent from `AlarmBroadcast.resumeIntent`). It has its own PendingIntent identity, so `rescheduleAll` never touches it. It is cancelled when the ring ends. If the process dies, by a crash, the memory limiter or Stop in the task manager, the entry fires within a minute, `AlarmReceiver` calls `RingController.resumeRinging` and the service starts with the alarm clock allowance. `resumeRinging` rings only if the record still describes that ring.
- `recoverInterruptedRing` on process start. It waits 2 seconds, and if the record is still not live it sets the watchdog entry 5 seconds ahead. This is what happens after a reboot, which wipes every alarm clock entry. Nothing on the boot path starts the service itself, because audio started there is muted. Whether audio from an alarm clock entry that fires seconds after boot is allowed has not been checked on a device.
- The service returns `START_REDELIVER_INTENT`, and a redelivered or retried start resumes the ring too. The system delays that restart, often by minutes, so the watchdog usually comes first.

A resumed ring does not ask whether its alarm is still enabled, and it keeps the barcode rule stored in its record. The record also lists the barcodes the ring started with, and a resumed ring takes those as well as the ones on its alarm now. Switching the alarm off, deleting its barcodes or deleting the alarm in the app and then killing the process does not silence it, and the scanner still works.

- A record whose 30 minutes ran out, or whose watchdog entry cannot be set, is cleared and reported as a missed alarm. If its deadline is still ahead, the fired record is removed and a one-shot alarm stays on, so it rings at the deadline.
- A persisted ring whose deadline passed without a fired record is reported as missed by `rescheduleAll`.
- A force stop from Settings cancels every alarm and cannot be closed by any app.

A snoozed ring survives too. Its record is in `RingStateStore.snoozed`, and its entry outlives the process. After a reboot `recoverInterruptedRing` shows each persisted snooze again, posts its notification and sets its entry again: at its time, or 5 seconds ahead when that has passed (after the same 2 second grace for an entry that is firing). A snooze more than 30 minutes overdue, or one whose entry cannot be set, is cleared and reported as a missed alarm, with the same rule for a deadline still ahead.

The test alarm uses id `AlarmBroadcast.TEST_ALARM_ID`. It goes through the same receiver, service and dismissal. It has no stored alarm, so it rings with an alarm's default tone, volume and snooze, needs no barcode, is not marked fired, is not in the plan and does not touch the session.

## Storage rule

Everything the scheduling and ringing paths read lives in device-protected storage: alarms, barcodes, settings, the sleep session and `RingStateStore`. The receivers, the service and the ringing activity are `directBootAware`. Nothing created during `Application.onCreate` may touch credential-protected storage. A user-picked ringtone may be unreadable before the first unlock, so the player falls back to the bundled tone.

ML Kit initialises itself from a content provider that is not direct boot aware. `ScannerCamera` initialises it by hand when that provider has not run. CameraX has the same problem with the service it reads its configuration from, so `RemApplication` implements `CameraXConfig.Provider`. The CameraX controller is built inside `ScannerCamera.bind`, so a scanner that still cannot start reports a camera error, and the screen offers the typed fallback and an unlock button.

`ScannerCamera` hands ML Kit the main executor for its results. An executor that can be shut down must not be used there: ML Kit delivers a cancellation after `release`, and a rejected task would crash the process on the main thread.

## Network

The app does not use the network. The manifest removes `INTERNET` and `ACCESS_NETWORK_STATE`, which ML Kit's logging library would otherwise merge in. `RemApplicationTest` checks the merged manifest.

## Tests

`:core` has plain JUnit tests. `:app` tests run on the JVM with Robolectric and coroutines-test: contract tests for every repository (run against Room, DataStore and the in-memory fakes), the scheduler against Robolectric's AlarmManager, the ring controller with a fake service launcher, the view models, `TonePreview`, `MigrationTest` (builds version 1 and version 2 database files by hand and opens them with `RemDatabase.open`, so Room checks the migrated schema), and `AlarmFlowTest`, which runs whole flows on the real container. Nothing automated covers the service, the audio classes, the camera or the Compose screens. Those get checked by hand on a device.

## Build

CI (`.github/workflows/build.yml`) runs `./gradlew :core:test :app:assembleDebug :app:testDebugUnitTest` on every push and uploads the debug APK as the `rem-debug-apk` artifact.
